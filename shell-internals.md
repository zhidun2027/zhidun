## 2. Hardening (Packing) Technical Principles

Core class: `com/frame/SignShellUtils.java`. The overall approach is **"extract the original dex → encrypt → embed into the shell → re-sign"**:

1. **Unpack**: use `apktool` to decompile the target APK into `source/`, yielding dex / resources / `lib/`.
2. **Encrypt the original code**: encrypt the original dex with the custom cipher (`com.utils.b`, see Section 3); the key is **randomly generated on each build**:
   - `SignShellUtils.java:403` → `string7 = "z" + System.currentTimeMillis() + "z"`
   - `:409` stores the encrypted dex as a resource inside the shell; key = `random string + "_" + version number (com.frame.a.a)`.
3. **Generate the key table**: pack the information needed to restore the original program into a HashMap, then serialize + encrypt it and write it into the shell APK's **`assets/cls_key`** (`:513-514`). The fields include:
   - `dexKey` (original-dex decryption key), `init_pass`, `init_md5`, `playMd5`, `signa` (signature), `version`, `sysTime`, `time`, `setting`, `pckName`.
4. **Inject the shell payload**: the shell's native library / loader comes from `config.dll` (see Section 4); at runtime the shell reads `assets/cls_key`, decrypts it, and dynamically loads the restored original dex.
   - `SignShellUtils.java:698-700`: takes `lib` from the shell and decrypts it with `com.utils.b.b("2025_09", …)`.
5. **Align + re-sign**: `zipalign` performs alignment, then `apksig` does v1/v2/v3 signing (`:621-632`, v4 disabled).

**Runtime protection switches** (checkbox options in the UI, written into the shell config): Hook check, HTTP proxy check / close proxy, ROOT check, VPN check, app-cloning detection, disable debuggable, developer-options check, 4-byte alignment. Saved to disk — see `com/frame/a.java:913-917`.

## 3. Encryption Algorithm (`com/utils/b.java`)

**A custom "repeating-key stream cipher," not standard AES**, at obfuscation-level strength. Global constants: `d=3`, `e=5`; base key `a = "2025-03-33"`.

For each byte `i` (the key cycles by its length, `key[i % len]`):

| Method | Purpose | Operation |
|---|---|---|
| `a(key,data)` | **Encryption** | `b ^= key[i]; b ^= 3; b -= 5` |
| `b(key,data)` | **Decryption** (inverse of a) | `b += 5; b ^= 3; b ^= key[i]` |
| `d(key,data)` | Pure XOR (used for the signa signature) | `b ^= key[i]` |

- The keys are all "date strings" (see Section 6). Because these are symmetric bitwise operations, knowing the key is enough to decrypt — no asymmetric crypto, no salt.
- `com.utils.c.java` also provides standard MD5 (used by `init_md5/playMd5` verification); `com.utils.e.java` reads the certificate serial number / SHA1 / SHA256 (for UI display); `com.utils.i.java` uses `Runtime.exec` to invoke apktool/java/zipalign.

## 5. ★ Trial / Counting / Validity Mechanism (the focus of your question)

**Conclusion: there is no "usage-count metering," no machine-code binding, and no online activation server. The only restriction is a time bomb tied to `config.dll`.**

- The check is at `SignShellUtils.java:298-305`:
  ```
  l2 = FileUtils.b(config.dll)                       // see below
  l3 = System.currentTimeMillis() - l2               // elapsed milliseconds
  if (l3 as days > 540) {
      popup "config.dll configuration file has expired; please re-download before use" ; stop
  }
  ```
- `FileUtils.b()` (`com/utils/FileUtils.java:110-114`) returns the **config.dll file's "creation time"** (`BasicFileAttributes.creationTime()`), **not** a timestamp embedded inside it.
- So the validity = **540 days from the moment config.dll is created on the local machine**. After expiry you must obtain a fresh config.dll (a refreshed creation time is enough to keep going). This is also why it keeps the resources separately in `config.dll` — using it as a "renewal switch."
- The "key 111111 / alias 11111111" in notes.txt is the **default signing password of the bundled test keystore (bj.keystore)** (the test main at `SignShellUtils.java:649-651` uses these same three values too) — **not** a license code; the "¥18 unlock" means buying the tool from the author at QQ 931656520, not an in-software unlock.

> In other words: this tool's "anti-freeloading" measures are very light — relying solely on config.dll's 540-day file-creation validity. It is **disconnected** from any licensing system that would require network access / machine code / usage counts.
